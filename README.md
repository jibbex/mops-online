# MOPS

MOPS is a web-based educational model computer with an integrated assembler and a
von Neumann machine simulator. It is designed to help students understand how a
simple CPU fetches, decodes, and executes instructions.

**Live application:** <https://jibbex.github.io/mops-online/>

## Features

MOPS provides a complete, browser-based environment for writing and running
assembly programs on a simplified von Neumann machine.

- A source editor with line numbers, syntax highlighting, and inline diagnostics.
- A two-pass assembler with symbols, forward references, and source maps.
- A machine-code listing that shows the generated object program.
- A virtual machine with fetch, decode, and execute phases.
- A live SVG diagram of the model computer.
- Visible registers, memory cells, buses, and control signals.
- One cyan data packet for every real transfer between units.
- Run, pause, step, and stop controls.
- Configurable execution modes and animation speed.
- Input and output registers with validation and blocking dialogs.
- Runtime traps for division by zero, overflow, and invalid instructions.
- Execution history with backward stepping.
- English and German interfaces with established technical terms.
- Fluid header and status typography for high-resolution displays.
- Responsive layout with a machine/editor switch on small screens.
- Light, dark, and system themes with a modern gradient palette.
- An instruction reference generated from the canonical ISA.
- Plain source file export and import for Moodle submissions.

### Usage

1. Write an assembly program in the editor or load an example.
2. Assemble the program.
3. Resolve any diagnostics shown in the editor.
4. Inspect the generated machine code in the listing view.
5. Start the program and observe the data packet on the bus between units.
6. Pause, step, or rewind to inspect individual states.
7. Enter a value when the input register requests one.
8. Confirm each output value in the output dialog.
9. Switch the interface language and theme from the header.
10. Download the `.asm` source file from the file dialog and upload it to Moodle.

### Moodle Tasks

Moodle links can pass a task identifier, a display title, and an interface language:

```text
https://jibbex.github.io/mops-online/?task=42&title=Summe&lang=de
```

The task identifier and title appear in the header for orientation. To submit an
exercise, open the file dialog, download the `.asm` source file, and upload it to
the Moodle assignment. The same file can be imported later to restore the source
code. The task link is optional; without it, the application runs in free-practice
mode and uses the file name `mops.asm`.

The source file is the only submission artifact. Machine code is regenerated by the
assembler, so the source remains the single source of truth. Instructors can open a
submitted `.asm` file directly in the application to verify and run it.

## Development Setup

### Requirements

- Node.js 22.12 or newer (LTS recommended).
- npm, included with Node.js.
- Git.
- Playwright browser binaries.
- On Linux, the system dependencies required by Playwright.

Bun is optional for running scripts. Node.js remains required because Vitest and
Playwright run on Node.

### Installation

#### Windows

```powershell
git clone https://github.com/jibbex/mops-online.git
cd mops-online
npm ci
npx playwright install
```

#### Linux

```shell
git clone https://github.com/jibbex/mops-online.git
cd mops-online
npm ci
npx playwright install --with-deps
```

`--with-deps` may require elevated permissions, depending on the distribution.

Use a current Node.js LTS release and run the commands from the repository root.

### Configuration

No environment variables are required for the default local setup.

The application accepts optional URL parameters:

- `task` or `taskId`: Moodle task identifier stored in exported solutions.
- `title` or `taskTitle`: Task title shown in the header.
- `lang`: Interface language, `en` or `de`.

The interface starts in the browser language and uses English for unsupported
languages. A stored language or theme preference takes effect on the next visit.
The `lang` parameter overrides the stored language for Moodle deep links.

### Run

```shell
npm run dev
```

### Test

```shell
npm run lint
npm run format:check
npm run typecheck
npm run test:unit
npm run test:e2e
```

Install the Playwright browsers before running the end-to-end tests:

```shell
npx playwright install
```

### Troubleshooting

- **Node.js version mismatch:** install a current LTS release and reinstall
  dependencies with `npm ci`.
- **Playwright browser missing:** run `npx playwright install`.
- **Playwright system dependencies missing on Linux:** run
  `npx playwright install --with-deps`.
- **Port already in use:** stop the conflicting process or change the Vite
  development port.
- **Stale dependencies:** remove `node_modules` and run `npm ci`.

## Deployment

### GitHub Pages

The `CI` workflow deploys the production build to GitHub Pages on every push to
`main`, after formatting, linting, type checking, unit tests, end-to-end tests, and
the build pass.

Enable GitHub Pages once in the repository settings:

1. Open **Settings > Pages**.
2. Set **Build and deployment > Source** to **GitHub Actions**.

The application is available at <https://jibbex.github.io/mops-online/>.

The workflow builds with the repository name as the Vite base path, so project
sites work without further configuration. For a custom domain or a user site, set
`VITE_BASE_PATH` to `/` in `.github/workflows/ci.yml` and configure the domain in
GitHub Pages.

### Local Production Build

```shell
npm ci
npm run build
npm run preview
```

To verify the project-site base path locally:

```shell
npm run build -- --base=/mops-online/
npm run preview -- --base=/mops-online/
```

### Other Static Hosts

The build is a static application in `dist/` and needs no application server or
database. Set Vite's base path to the host path before building.

### Maintenance

- Update dependencies deliberately and review the changelogs.
- Run linting, type checking, unit tests, end-to-end tests, and a production build
  before deploying.
- Verify the production bundle does not contain development-only code.
- Reinstall Playwright browsers after major Playwright upgrades.

## Project Structure and Architecture

```text
src/
  components/       Application shell, editor, SVG diagram, dialogs
    ui/             shadcn/ui primitives used by the shell
  core/
    isa/            Instruction set definitions and opcode metadata
    object/         Object program, listing, and machine limits
    assembler/      Scanner, parser, encoder, resolver, diagnostics
    vm/             CPU state, micro-ops, execution, traps
  i18n/             English and German messages and language provider
  lib/              Source file exchange, task metadata, formatting
  player/           Timing, playback, history, and visual event mapping
  styles/           Diagram tokens and SVG animation styles
  test/             Shared test setup and fixtures
  app.tsx
  main.tsx
tests/
  e2e/              Playwright user-visible flows
LICENSE
README.md
```

Core ideas:

- The assembler produces an object program; the VM executes only that object
  program.
- The VM does not know about source text, labels, comments, or mnemonics.
- Source maps connect machine-code addresses back to editor lines.
- The player owns timing, pausing, input handling, and execution history.
- The UI renders state and visual events; it contains no machine logic.
- The diagram is rendered with SVG and styled with CSS variables.
- shadcn/ui components live in `src/components/ui` and are used only for the
  application shell, never for the SVG diagram.

Tech stack:

- Vite
- React
- TypeScript
- Node.js LTS and npm
- Tailwind CSS for the application shell
- shadcn/ui for application shell components
- CSS variables and a dedicated stylesheet for the SVG diagram
- CodeMirror 6
- Zustand
- Vitest
- Testing Library
- Playwright
- ESLint
- Prettier
- Husky
- commitlint

Common additions:

- **New instruction:** add its opcode to `src/core/isa/opcodes.ts` and its
  operand modes, execution sequence, and metadata to
  `src/core/isa/instructions.ts`. Parser, encoder, and VM derive their behavior
  from that table; add a new ALU operation only when the instruction needs
  semantics that do not exist yet.
- **New diagram element:** add its layout data, SVG component, visual mapping,
  fixture, and Playwright coverage.

### Scope

MOPS implements a simplified educational model computer.

It includes:

- a 72-cell memory,
- a 15-instruction assembly language,
- an assembler with symbolic labels,
- a fetch-decode-execute VM,
- a live SVG visualization,
- debugging and execution history.

It does not include:

- a real processor or native machine code,
- indirect addressing,
- processor flags,
- bit manipulation,
- macros or compiler directives,
- a high-level language.

### Arithmetic Semantics

MOPS uses the original model computer's decimal, fixed-width arithmetic:

- machine words are integers from −9999 to 9999,
- division is floor division (`div` rounds toward negative infinity),
- modulo keeps the sign of the divisor,
- results outside the word range trap instead of wrapping.

Examples: `-7 div 2` is `-4`, `-7 mod 2` is `1`, and `7 mod -2` is `-1`.
These rules match MOPS 1.04, which uses Python's `operator.floordiv` and
`operator.mod`. They are covered by the VM semantics tests.

### Program Counter

The program counter (`PC`) is an **instruction index**, not a memory address. It
advances by exactly one per instruction, including `end`, independent of the
two-cell instruction encoding. The VM maps the PC to the instruction's memory
address through the object program, and jumps set the PC to the target
instruction index.

The counter is incremented in the fetch phase (`PC_UPDATE`), after the
instruction has been copied into the instruction register.

Active diagram elements carry one of three operations: **read**, **write**, or
**increment**. The same visual language is used everywhere: reads are soft and
dashed, writes are solid and filled, and increments add a packet-colored pulse.
This keeps `PC_READ`, `MEM_READ`, `AC_READ`, and every other read distinct from
a write or an increment without introducing per-component styles.

### Conventions

- All repository text is written in American English.
- Indentation uses four spaces.
- Line endings use LF.
- Control-flow blocks always use braces.
- Opening braces stay on the same line.
- Closing braces start a new line.
- `} else {`, `} catch (...) {`, and `} finally {` stay on one line.
- Commit messages follow Conventional Commits.
- The scope is optional.
- Branches use prefixes such as `feat/`, `fix/`, and `docs/`.
- Merges use squash merge with a Conventional Commit title.
- Comments explain why, invariants, and trade-offs; they do not narrate code.
- Behavior, limits, timings, and capacities use named constants instead of
  magic numbers.
- ESLint handles linting; Prettier handles formatting.
- `eslint-config-prettier` disables conflicting ESLint formatting rules.
- Source imports are limited to 16 KiB and report a specific reason when they
  are empty, oversized, unreadable, or binary.
